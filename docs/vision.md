# 平台最终目标与愿景（Vision）

> 本文档记录平台的最终目标。后续所有开发、修复与改进都应朝着这个方向推进，
> 并以"是否更接近这个目标"作为优先级判断依据。

## 愿景

让全世界范围内的用户在平台上注册、创建各种有价值有意义的仿真环境，
并借助这些环境创建全新的 AIoT 应用（尤其是 AI Agent 驱动的产品原型）。
当应用在仿真环境中成功运行后，用户可以轻松地将其部署并迁移到现实世界；
他们还可以选择是否将现实中的部署反向映射回仿真环境。

因为 LLM 存在大量不确定性，本平台的价值在于：让用户能够在低成本、可重复的
仿真环境中，验证"基于 Agent 的想法在 IoT 上是否可行"。

## 用户视角的成功标准

一个用户在平台上应能完成以下完整链路，这也是模拟用户测试时必须逐项验证的：

1. **创建与部署设备**：成功借助平台创建和部署 IoT 设备（真实型号名录，一键放置）。
2. **Agent 管理设备**：借助平台提供的认知 Agent 管理自己的设备。
3. **Resource / Service 抽象**：成功运用 resource 与 service 的抽象（设备私有、服务公开、
   Agent 绑定设备自动派生服务）。
   （实现注记：环境级服务注册表 + 派生单源
   `packages/core/src/service/device-service-derivation.ts`；服务带
   origin/semanticType/summary/visibility 元数据。）
4. **应用有效性**：创建的 IoT 应用是有效的，并能在仿真环境中真实运作（空间物理 +
   LLM 决策）。
5. **跨用户协作**：借助共同的仿真环境与其他用户创建的 Agent 沟通，发现并消费其他
   Agent 暴露的 service，利用他们的设备与功能，并在此协作基础上创建出新的应用。
   （实现注记：世界层目录经 catalog-sync 镜像进 live runtime，场景即代码声明语义
   offer（`services`/`semanticOfferRules`/`capabilitySynonyms`），决策 prompt 注入
   目录 digest 与伙伴 shortlist；AC 握手落 ephemeral agreement 自动计量。）
6. **体验记录**：每个模拟用户都应记录自己的平台使用体验（可用性发现归档到
   [usability-findings.md](usability-findings.md)）。

## 平台视角的目标

- **生态价值评估**：我们最重要的判断是——这个平台是否有成为一个繁荣、被广泛使用的
  生态平台的价值。模拟大量不同用户的探索与测试，是发现平台实现层面问题、
  进行系统性修复与改进的主要手段。
- **AI 训练场**：当有足够多的用户与环境后，平台可以：
  - 借助平台训练和调试特别适应 IoT 环境的 Agent；
  - 让 Agent 通过平台接口访问一个足够接近现实世界的空间，
    在其中训练出更全面、更强大的 AI。
  落地入口（Fix-22）：`GET /api/environments/:id/training-export` 导出
  决策 + 环境时序 + 消费计量 + 声誉的训练数据（NDJSON），
  `GET /api/simulations/:id/eval-report` 输出单次仿真的决策质量指标。
  跨运行学习（R6-E-F15）：agent 的私有经验（决策校准 + 私有伙伴信任）
  按 (env, agent) 持久化，sim 重建不归零——"agent 越用越聪明"的最小
  可行步，与平台声誉的共享信号互补。

## 决策引擎定位（R74 起为平台约定）

- **LLM 决策是唯一的生产形态**。平台的生产价值建立在 LLM 驱动的 Agent 认知
  （情境评估 → 协作决策 → 设备行动）之上；生产部署必须配置 LLM 后端
  （`LLM_BASE_URL` + `LLM_MODEL`，vLLM 为唯一后端）。
- **规则引擎是测试线束，不是降级的生产**。无 LLM 时的确定性规则路径只服务于：
  回归测试、训练数据管线、无 GPU 环境下的机械演示。它**不能**体现平台的
  生产价值——规则会"响应"事件，但那不是智能体行为。
- **模式必须始终显式**。服务器在 `/api/health` 暴露 `decision.mode`：
  `llm` = 生产姿态（后端配置齐全**且**存活探测通过）；`llm-unreachable` =
  已配置但后端不可达（决策正在退化为规则，姿态受损，红色横幅示警）；
  `rule-test` = 测试姿态（琥珀色横幅标注"仅测试"）。任何用户与程序都不应
  把规则驱动的行为误认为生产级行为。

## 对开发工作的指导意义

- 新功能或重构前，先问：它是否让用户更接近"仿真验证 → 现实部署"的完整链路？
- 发现实现层面的 bug 或可用性问题（尤其来自模拟用户测试的），优先系统性修复，
  而不是局部打补丁。
- 保持 AI 友好的三通道（Web UI / CLI `--json` / OpenAPI 契约）始终可用且语义一致，
  因为未来的用户和 Agent 都依赖它们。
