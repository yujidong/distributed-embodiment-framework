# 平台使用教程：从观光客到生态共建者

> 本教程带你在约 30 分钟内完整体验 embodied-agent-framework 平台：
> 看懂生态 → 从零建世界 → 把服务嵌入城市 → 仿真验证 → 输出部署清单。
> 你将扮演一家夜间接驳创业公司「星夜出行」，最终把自己的服务接入苏州智慧城市。
>
> 想找**教学楼仿真与协作治理**（提案审批/沙箱/回放）的 curl/CLI 实操任务线，
> 走姊妹篇 [docs/tutorial-smart-campus.md](tutorial-smart-campus.md)。
>
> 只想**先跑起来看看**（10 分钟）：工作台「+ 新建环境」→「模板」tab，
> 19 个内置场景一键创建（来自 `GET /api/scenario-templates`；
> CLI 等价：`eaf scenario-templates list / show <id>`）——推荐最小世界
> starter-home（3 区域 + 3 设备 + 1 Agent + 4 个演示事件），跑通后可继续
> 挑战智慧酒店、社区养老院、智慧农场等模板。喜欢走命令行的话，场景 JSON
> 都在 `config/scenarios/`，导入方式与教学楼相同（见
> tutorial-smart-campus.md 第 2 节，把文件路径换成它即可）。

## 0. 一分钟概念

| 概念 | 说明 | 教程里在哪出现 |
|---|---|---|
| 环境（Environment） | 一个共享世界：地图 + 区域 + 设备 + Agent + 服务 | 第一章～第五章 |
| 区域（Zone） | 世界里的空间单元（房间/街区），有物理参数 | 第二章创建 |
| 设备（Device） | 私有资源，归属创建者；可被 Agent 绑定 | 第二章放置 |
| Agent | 认知主体，绑定设备获得"身体"，用 LLM 做决策 | 第二、三章创建 |
| 服务（Service） | Agent 对外提供的能力契约，**跨 owner 的可见性边界** | 第三章发布 |
| 协作（AC） | Agent 发现自己搞不定时，按能力契约寻找伙伴、组成协作 | 第四章观察 |

三条设计原则先记住：**设备私有，服务公开**；**模型编写，框架校验，执行器执行**；**仿真里验证过的，才往真实世界搬**。

## 1. 准备工作

```bash
# 终端 1：API 服务（需要 LLM 时先起 vLLM：vllm serve Qwen/Qwen3-14B
#   --served-model-name qwen3-14b-q4:latest，见 docs/deployment.md §5）
cd embodied-agent-framework
LLM_PROVIDER=vllm LLM_BASE_URL=http://127.0.0.1:8000/v1 LLM_MODEL=qwen3-14b-q4:latest \
  node apps/server/dist/index.js        # http://localhost:8100

# 终端 2：前端
npm run dev -w @active-collaboration/web  # 看输出的端口，如 http://localhost:5173
```

> 没有配置 LLM（vLLM 等 OpenAI 兼容端点）也能浏览和建世界，但 **Agent 协作决策需要 LLM**——rule-only 模式下看不到协作发生。

打开前端，注册账号（邮箱 + ≥8 位密码 + 昵称，例如昵称为"星夜出行"）。登录后进入**工作台**——这是"你"在平台里的位置。

**验收**：工作台为空（你还没加入任何环境），顶部有「浏览环境」入口。

## 2. 第一章：观光——看懂生态（5 分钟）

目标：在最大规模的现成世界里，理解设备、Agent、服务、协作的关系。

1. 工作台 →「浏览环境」→「公开」标签 → 找到 **苏州智慧城市**，点「加入」（成为 builder）。
2. 进入环境。你看到的是真实苏州地图（右下角可切 标准/清爽/暗色/卫星/高德 底图，
   视图可切 平面/地理/3D，多楼层世界还有「楼层」tab 与楼栋聚焦）：
   - 9 个多边形片区、33 个彩色圆点（设备）、12 个六边形标记（Agent）。
   - 左上角图层开关可以分别隐藏 区域/设备/Agent/协作边。
3. **点「环境监测中心」这个 Agent**：虚线连向它遍布全市的监测站——"一个脑，N 个身体"。
4. 侧栏切到「服务」tab（服务市场）：
   - 按语义类型分组，你能看到 89+ 个派生服务和 7 个发布服务；
   - 找到「网约车运力调度服务」（滴滴发布）和「需求响应负荷聚合服务」（国网发布），点进去看接口定义；
   - 注意 ⚠无支撑 标记：平台型公司没有设备，服务是它们对世界的承诺。
5. 点右上「全局视角 / 我的视角」切换——现在你什么都还没建，"我的视角"是暗的，这正是第三章要改变的。

**验收**：能说出"谁有什么设备、谁提供什么服务、服务和设备的派生关系"。

## 3. 第二章：安家——从零建我的小世界（10 分钟）

目标：完整走一遍"空白环境 → 区域 → 设备 → 多个 Agent → 服务"的创建流程。这是你自己世界的预演。

> 更快的路径：「新建环境」对话框的「**模板**」tab 可一键创建 19 个内置场景
> （区域/设备/Agent/事件全配好）；「导入场景 JSON」tab 支持粘贴 JSON 或
> 从文件选择器导入，作为进阶用法保留。本章仍走手工路径，是为了看清每个概念。

1. 工作台/环境首页 →「+ 新建环境」→「空白环境」tab：名称 `星夜出行调度站`，可见性选"公开"。
2. 进入新世界（空空如也）→ 侧栏「设备」tab →「区域管理」→「新建区域」，建两个区域。
   区域由**边界（bounds）**定义，是四个必填参数（单位：米）：`minX / maxX / minY / maxY` 圈出平面矩形，
   另有一对**可选**参数 `minZ / maxZ` 表示高度或楼层范围（比如 0~3 表示一层）——
   引擎的空间物理是三维的，跨楼层的效应传播会按 z 距离衰减：
   - `office`（调度中心）：`{minX: 0, maxX: 6, minY: 0, maxY: 5}`，baseline temperature 26
   - `garage`（车队停车场）：`{minX: 6, maxX: 14, minY: 0, maxY: 5}`，baseline temperature 30
3. 「新建设备」，放三台（类型/能力按建议选）：
   - 办公室：温湿度传感器 `[temperature-monitoring]`
   - 停车场：智能电表 `[energy-monitoring]`（也可从「名录」tab 搜"电表"放置，带真实型号和价格）
   - 停车场：照明 `[lighting-control]`
4. 侧栏「Agent」tab →「新建 Agent」，建**两个**（一个 owner 多个 Agent 是常态）：
   - **感知员**：能力 `[temperature-monitoring, energy-monitoring]`，绑定传感器 + 电表，管理两个区域。它只有感知能力——**必须求人才能行动**，这是协作的种子。
   - **运维员**：能力 `[lighting-control]`，绑定照明设备，LLM 配置保持默认（openai-compatible/vLLM，模型 qwen3-14b-q4:latest）。
5. 「服务」tab 确认：绑定后自动派生出服务（每台设备 × 每个能力一条）。给运维员的照明服务改可见性为"成员"。

**验收**：地图上有 2 个区域、3 个圆点、2 个六边形；服务市场出现你的派生服务。

> 不想手工搭？侧栏「**蓝图**」tab 可一键安装应用模板（设备 + Agent + 业务流
> 的组合包），装完即是一组可运行的服务——适合快速给空白世界"上装备"。
> CLI 等价：`eaf blueprint list`、`eaf blueprint install <blueprintId>
> --env <id|name> --zone <zoneId>`。

## 4. 第三章：入伙——把我的服务嵌入城市（5 分钟）

目标：以商业主体身份进入共享城市，发布服务、标记依赖。

回到 **苏州智慧城市**（你已是 builder）：

1. 「Agent」tab →「新建 Agent」：
   - 名称 `星夜出行运力中心`；
   - 能力**留空**（纯软件主体不声明能力）；
   - **不绑定任何设备**（车队是虚拟的——纯软件主体）；
   - LLM 选默认（vLLM 后端）。
   > **平台规则（能力必须有设备背书）**：Agent 声明的每一项能力都必须由它绑定的
   > 设备实际提供——无设备 Agent 的能力列表必须为空，否则提案会被规则校验直接驳回
   > （`... are not provided by any bound device`，CLI `eaf agent add` / API 同口径；
   > hass:// 真实硬件豁免）。这不影响"纯软件主体"玩法本身：Agent 照建，
   > 你的商业承诺走下一步的「发布服务」。
2. 「服务」tab →「发布服务」：
   - 名称 `夜间接驳运力服务`，语义类型 `night-shuttle`；
   - 描述：面向大型活动散场、恶劣天气的夜间集中运力调配；
   - 接口加两行参数：`area`（服务区域）、`fleetSize`（可调度运力）；
   - 可见性：公开。
   - 注意它带 ⚠无支撑 标记——正常，滴滴/美团的服务也是这样存在的：**发布服务是对世界的承诺**，不要求设备背书（与 Agent 能力声明不同）；它会被标记 `consumable:false`，即别人能发现你、但不能直接签约调用，等你后续绑定真实运力设备后即可交付。
3. 标记你的依赖（服务市场里点 ★）：
   - 「路况/车流」类（交通管理局的派生服务）
   - 「需求响应负荷聚合服务」（国网）
4. 切到「我的视角」：你的 Agent 和服务高亮，其他资产淡成背景——**你在城市里有位置了**。

**验收**：「我的视角」下能看到自己的六边形；工作台的城市卡片显示 我的Agent 1、我的依赖 2。

## 5. 第四章：验证——仿真与协作观察（10 分钟）

目标：证明你的服务真的能嵌入城市的协作网络。

1. 城市环境 →「运行仿真」（LLM 模式选 **auto**，确认 vLLM 在跑）。
   第一次跑建议速度选「**演示 ×60**」（三档：实时 ×1 / 演示 ×60 / 极速 ×400）
   ——演示档下几分钟就能看到城市剧本完整上演。
2. 城市剧本会自动上演（晚高峰 t=30、PM2.5 t=60、用电高峰 t=120、暴雨 t=180、交通事故 t=240、大型活动散场 t=300）：
   - 观察**协作图**：Agent 节点间出现动态边；
   - 观察**事件日志**：协作提案逐条滚动；
   - 观察 zone 上实时参数变化和决策气泡。
3. **主动让世界来找你**：展开右侧抽屉的「事件注入」面板，注入一个自定义事件——
   - 类型 `night-shuttle-demand`，区域 `jinji-lake`（金鸡湖），参数 `passenger-flow`，值 `5000`，severity `high`。
   - 如果城市里的 Agent 评估后认为需要接驳运力，而你发布的「夜间接驳运力服务」（语义类型 `night-shuttle`）进了它的候选清单——**协作提案会发到你的 Agent**。
4. 顶部进入「回放」，拖时间轴复盘刚才的协作形成过程；底部抽屉的「评估」tab
   有本次仿真的决策质量指标。
5. 点你的 Agent 看决策详情：它为什么发起/接受/拒绝了协作。

> **说明**：协作由 LLM 按能力契约自主决策，不是脚本——多试几次、调整你的能力和接口描述，观察命中率变化。这个"调优"过程本身就是平台的价值。

**播放速率与墙钟**（R39 实测口径，避免把"×60"当成的墙钟倍速）：

- 「速度」档位的数字是 **speed = 每 tick 推进的仿真秒数**，不是墙钟倍速。三档 实时 ×1 / 演示 ×60 / 极速 ×400，即每 tick 前进 1 / 60 / 400 sim 秒。
- 引擎默认每 **10ms 墙钟**走一个 tick（`tickMs`），理论上限 ≈ speed × 100 sim 秒/墙秒；tick 执行本身有开销，R39 实测 speed=10 时约 **600–1000 sim 秒/墙秒**。换句话说，一个"十分钟世界"（600 sim 秒）在演示档下约 1 秒墙钟就走完——你看到的是压缩快进的剧本，不是实时直播。
- **名义 vs 实际**（T3，R2 实测口径）：tick 循环是自适应的——一个 tick 的真实耗时超过预算时，下一个间隔拉长为 `max(tickMs, lastTickWallMs × 1.2 + 1)`（LLM 决策、事件循环拥堵都会拉长），所以**实际推进速率常低于名义值且随负载波动**（R2 实测：名义 ×300 的世界，实测在 ×34–×222 之间波动）。`sim status`（human 与 `--json`）透出 `tickMs`、`lastTickWallMs`、`autoThrottled` 与换算依据 `effectiveSpeedPerSec`（= speed ÷ 有效 tick 间隔，围绕最近一个 tick 的**瞬时估计**）；`autoThrottled=yes` 即"实际推进低于名义值（tick 被节流）"。 **T32/T43（R3→R4）口径注**：瞬时估计随 LLM 负载波动可达 2–4 倍，`sim status` 双口径并列——`effectiveSpeedWindowPerSec`（最近 ~60s 墙钟的滑动窗口均值，刚启动/暂停态诚实缺席）是**排期以窗口口径为准**的那个数，瞬时值只用于观察尖峰。运行中改档不必先暂停：对 running 世界 `sim resume --speed N`（API 同）就地 retarget，下一 tick 生效（响应带 `speedRetargeted: true`）。
- 「回放」面板的播放速率（场景 meta `recommendedPlaybackRate` 只是初始种子）是另一码事：它表示**每 250ms 前进多少个缓冲快照**（回放游标步进），与世界墙钟倍速无关。
- 手动步进（Web「步进」按钮 / CLI `eaf sim step` / API `step`）的 **n 是 tick 数**，不是 sim 秒——`n × speed` 才是实际推进的仿真时间。单次请求上限 **600 tick**（服务端 `EAF_MAX_STEP_TICKS` 可调），超限返回 422 `STEP_TOO_LARGE`（教学错误：提示分块步进，或世界会话改用 `toSimTimeSec` 直接给目标时刻）。
- **speed ↔ 墙钟倍率换算表**（DOC-02；默认 `tickMs`=10 时，名义墙钟倍率 = speed × 100；`start`/`resume` 响应与 CLI human 行会回显 `speed` 与 `nominalSpeedPerSec`，不用自己算）：

  | 想要的名义墙钟倍率 | speed（sim-s/tick） | nominalSpeedPerSec（sim-s/墙秒） |
  |---|---|---|
  | 实时 ×1 | 0.01 | 1 |
  | ×5 | 0.05 | 5 |
  | ×60 | 0.6 | 60 |
  | ×100 | 1 | 100 |
  | ×500 | 5 | 500 |
  | ×6000 | 60 | 6000 |

  反算公式：speed = 目标倍率 ÷ 100。lazy 调度的世界会话没有 tick 定时器，speed 直接是 sim-s/墙秒，回显里的 `nominalSpeedPerSec` 诚实缺席。

**验收**：事件日志里出现涉及你 Agent 的协作提案；回放能完整复盘。

## 6. 第五章：交付——部署清单（2 分钟）

目标：把"大家觉得你的服务不错"变成可执行的落地计划。

1. 城市环境侧栏 →「部署」tab，看你的**部署清单**：
   - 我的 Agent（星夜出行运力中心，含 LLM 配置）；
   - 待采购设备：空——平台会提示"纯软件主体：星夜出行运力中心 无绑定设备，部署仅需 Agent 与服务契约"（如果你在第二章那个环境看，则会列出 3 台设备的名录价格和采购链接）；
   - 我要提供的服务：夜间接驳运力服务（含接口定义）；
   - 我依赖的外部服务：你打过 ★ 的那两个，带着供应商名字——**这就是你上线前要签的契约清单**。
2. 点「导出 JSON」下载清单。这份文件就是你和硬件商、服务方谈判的输入。
   （CLI 等价：`eaf env deployment <id|name>`——人类模式打印采购清单摘要，
   `--json` 输出原始清单，Fix-13。）

> 「部署」tab 同时也是 Home Assistant 桥接向导（连接 HA → 绑定设备 →
> 安全闸 → 指令测试）——想把仿真里验证过的世界接到真实硬件，从这里走。

**验收**：能说清"要落地我的服务，需要买什么、暴露什么、签约什么"。

## 7. 进阶：给 AI agent 的三条通道

平台不只是给人用的——你的 AI agent 也可以成为平台的用户：

```bash
# 1. CLI（全部命令支持 --json，可管道）
alias eaf="npx tsx apps/cli/src/main.ts"
eaf auth login --email you@example.com --password ********
eaf env list --json
eaf apply -f my-world.yaml        # 声明式世界文档，幂等创建/更新
eaf sim watch <simId> --json      # NDJSON 持续输出运行 diff

# 2. OpenAPI 契约（agent 读完可自行拼装任意调用）
curl http://localhost:8100/api/openapi.yaml

# 3. 人类可读的 API 文档
open http://localhost:8100/api/docs
```

世界文档示例见 `apps/cli/examples/world.grid.yaml`，JSON Schema 在 `apps/cli/schema/world-document.schema.json`——把 schema 交给 LLM，它就能直接替你写世界。

## 8. 故障排查

| 症状 | 原因与处理 |
|---|---|
| 协作图一直安静 | 大概率是 rule-only 模式（无 LLM 不协作）。仿真创建时 LLM 选 auto，确认 vLLM 在运行、`--served-model-name` 与 `LLM_MODEL` 一致 |
| 地图瓦片不显示 | OSM/Carto/Esri 需要联网；高德需在 `apps/web/.env.local` 配置 `VITE_AMAP_KEY` + `VITE_AMAP_JSCODE` |
| 注入事件没反应 | 事件参数名要匹配（temperature/co2/pm2_5/smoke/humidity/light）；确认注入到了有 Agent 管理的区域 |
| 看不到别人的服务 | 服务可见性三级（公开/成员/隐藏）；隐藏服务只有提供者和环境所有者可见 |
| LLM_NOT_CONFIGURED | 服务器启动时未设置 `LLM_BASE_URL`/`LLM_MODEL`（vLLM 等 OpenAI 兼容端点），或后端未运行 |
| 端口被占 | Vite 自动顺延（5173→5174…），以终端输出为准 |
